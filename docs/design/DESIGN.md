# Rehearsal — Design

Design for the MVP described in [`../PRODUCT.md`](../PRODUCT.md): the shape of
the system, the constraints behind it, and the UI it produces.

## 1. Shape of the system

Four parts, and the seams between them are the whole design:

```
browser  ──  audio in/out, renders the scene, holds no secrets
   │  WebSocket (PCM up, PCM + event frames down)
   ▼
session  ──  one scene, one connection, one transcript
   │
   ├──▶ character  (the person you talk to — speaks, never corrects)
   ├──▶ coach      (watches the transcript — corrects, never speaks)
   └──▶ memory     (reads your past patterns in, writes today's out)
```

Two independent language models run per session. They never share a turn: the
character holds the conversation, the coach reads a copy of it and publishes
cards. That split is what lets the product promise *"never lectured mid-scene"*
structurally rather than by asking a model to behave — the character is simply
never told what the learner got wrong.

---

## 2. The three constraints that drive everything

`PRODUCT.md` lists eight "never" rules. Three of them are architectural, and
most of the design follows from them:

**Never ambiguous silence.** Voice has no cursor. The learner cannot tell
"thinking" from "broken", so the app must say which — hence an explicit state
machine (`listening → thinking → speaking`) rendered three ways: colour, label,
and Pip's expression.

**Never lectured mid-scene.** Feedback is *pull-shaped*, not push-shaped: cards
land in a rail the learner may never read, and the coach is silent by
construction. Corrections are capped so the rail can't become a wall of red.

**Never a dead end.** Mic failure, a silent learner, and a mid-sentence quit all
have a defined, non-punitive path. Nothing in the system can leave the learner
without a next action.

## 3. The loop

```
   ┌──────────────────────────────────────────────────────────┐
   │  scene card  →  goal + who + what's in the way           │
   └───────────────────────────┬──────────────────────────────┘
                               ▼
        ┌──────────────────────────────────────────────┐
        │  TURN LOOP                                   │
        │                                              │
        │   character speaks first (never a blank page)│
        │        ↓                                     │
        │   learner talks (or types)                   │
        │        ↓                                     │
        │   barge-in? cut the TTS, keep the transcript │
        │        ↓                                     │
        │   character replies ──┐                      │
        │   coach observes ─────┘ (parallel, silent)   │
        └──────────────┬───────────────────────────────┘
                       ▼
              End (or quit, or drop)
                       ▼
        ┌──────────────────────────────────────────────┐
        │  DEBRIEF — always produced, never skipped    │
        │  did you win · what worked · what to watch   │
        │  · every sentence, corrected · next scene    │
        └──────────────────┬───────────────────────────┘
                           ▼
                    memory writes back
                           ▼
        next session opens: "Last time you dropped past tense
        three times — let's see if it sticks."
```

## 4. Decisions worth arguing about

**Interruption is a first-class feature, not a bug.** Barge-in is on the
*never cut* list, so it is designed for: the learner's speech cancels TTS output
mid-word while the character's already-spoken text stays in the transcript.

**No overall score, no pronunciation score.** `PRODUCT.md` rules these out
because a bad number is both discouraging *and* unreliable. The debrief reports
counts and quotes instead — "three times", "you interrupted once and it landed".

**Feedback is written twice.** Every correction carries an English line (what to
say) and a Chinese line (why), because a correction the learner can't parse
teaches nothing. Chinese is a per-user toggle for learners who outgrow it.

**Typing is a peer mode, not a fallback.** It shares the transcript, the coach,
and the debrief; only the input surface changes. That keeps "the mic died" from
becoming a different, degraded product.

**Memory stores patterns, not transcripts.** The next session needs *"past tense,
three times"*, not yesterday's audio. This keeps the write small and the
callback specific.
